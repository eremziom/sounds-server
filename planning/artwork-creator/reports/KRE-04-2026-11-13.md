# KRE-04 — pierwszy przyrost interfejsu, 2026-11-13

**Etap w toku.** Na polecenie „Zacznij wdrażać KRE-04” powstał chroniony ekran
`/animations/create` i odnośnik na `/animations`. Działa zarządzanie projektem,
planem, zadaniami, obrazami i historią. Nie zamknięto kryterium pełnej produkcji
warstwowej sceny i animowanego podglądu z UI. KRE-05–KRE-08 nie rozpoczęto.

## Zakres plików i zachowanie

- `apps/ui/src/app/(protected)/(app)/animations/create/page.tsx`: dotychczasowy
  guard `APP_ROLES`, ekran wewnątrz istniejącego ApplicationRuntime/MediaRuntime
  i przekazanie tłumaczeń do klienta. `/animations/page.tsx`: odnośnik kreatora.
- `apps/ui/src/components/artwork-creator/artwork-creator.tsx`: tworzenie/wybór
  projektu, sześciopolowy plan bez JSON, zapis rewizji, PNG do 32 MiB,
  notatki, generacja źródła, postęp/anulowanie/ponowienie, świadomy wybór obrazu,
  statyczny widok obrazów i osobnych masek, porównanie oraz przywrócenie wersji.
  Niezapisany plan blokuje operacje zmieniające projekt; można go zapisać albo
  odrzucić. HTTP 409 zachowuje wpisany tekst i wymaga świadomego odświeżenia.
- `creator-session.ts`: atomowy odczyt widoku projektu, odrzucanie spóźnionych
  odpowiedzi po zmianie projektu, odświeżanie zadań/artefaktów bez resetowania
  formularza. Starszy polling nie zastępuje wyniku nowszej operacji. Powrót
  do wersji używa istniejącego API tworzącego nową rewizję; nie usuwa notatek
  ani plików. Wybranie obrazu zmienia tylko roboczą warstwę `source`, odłącza
  jej stare maski i dołącza wejścia nowego obrazu; pozostałe warstwy zachowuje.
- `apps/ui/src/api/artworks.ts`: typowany klient istniejącego API KRE-01/02,
  pełne stronicowanie projektów, rewizji, wiadomości i zadań. `generateImage`
  używa zapisanego planu i nowego klucza idempotencji; ponowienie niepewnego
  enqueue w tej samej sesji zachowuje klucz. Zapisów/konfliktów nie ponawia
  automatycznie. Po odświeżeniu należy najpierw sprawdzić odzyskaną listę zadań.
- `apps/ui/src/app/api/artworks/[...path]/route.ts` i `artwork-proxy.ts`:
  kontrolowany pośrednik korzystający z HttpOnly cookie. Allowlista tras/metod,
  UUID, kontrola Origin mutacji, limity bajtów, timeout także dla zablokowanego
  uploadu/odczytu odpowiedzi. Prywatne PNG/JSON bez obcych cookies, filename,
  nagłówków i szczegółów błędów. Dostęp do projektu nadal sprawdza API właściciela.
- `apps/ui/messages/{pl,en,es}.json`: tłumaczenia nowego ekranu; zachowane
  formatowanie istniejących sekcji. Testy w `apps/ui/tests/artwork-*` i bieżący raport.

API, modele danych, wykonawca, silnik oraz istniejące paczki nie były zmieniane.
Nie tworzono nowego artworku ani produkcyjnej paczki. Formularz zapisuje wersję
i link wspólnych wytycznych v1.7 oraz ich sceniczne zastosowanie podane przez
użytkownika. Istniejący worker konsumuje wspólne instrukcje i brief przy generacji;
UI nie zawiera drugiej kopii zasad ani nowego kompozytora promptów.

## Granice i następne prace

1. **Brak animowanego podglądu draftu.** Obecny host `browser-session.ts` przyjmuje
   tylko `VisualScene` i wbudowany katalog. Potrzebny adapter manifestu i
   prywatnych zasobów z walidacją, parkowaniem podróży i bezpiecznym powrotem.
   To stwierdzona różnica między docelową specyfikacją a kodem; nie obchodzono jej
   drugim rendererem, zegarem ani resetem podróży. Statyczny obraz nie stanowi QA
   ruchu/zoomu. Nie ma nowych dowodów jakości masek ani odbioru artworku.
2. **Brak pełnej produkcji warstwowej sceny z UI.** Przycisk uruchamia prawdziwy
   endpoint `generateImage`, ale test kontroluje kolejkę przez fixture HTTP.
   Nie uruchamiano Klein/SAM/LaMa ani istniejącego workera na danych użytkownika
   w tej próbie. Potrzebny jest nadal proces segmentacji/tła/map/budowy paczki
   dostępny przez UI oraz rzeczywista generacja i przegląd animacji.
3. Referencje PNG są zapisane i widoczne; `generateImage` w obecnym kontrakcie
   nie przyjmuje plików. UI wprost informuje, że generacja źródła jest tekstowa.
   Nie udaje image conditioning. Notatki nie są rozmową z modelem KRE-05.
4. Gotowość zależy od konfiguracji magazynu, działającego API/wykonawcy i bramki
   pamięci KRE-02. Ekran odzyskuje stan z API po odświeżeniu; sam nie uruchamia
   usług. Test nie dowodzi rzeczywistego restartu bazy/wykonawcy.
5. Nie ma publikacji/biblioteki KRE-07 ani pędzla masek KRE-06. Nie rozszerzono
   zachowań silnika, reguł portali lub integracji audio.

KRE-04 pozostaje **w toku**, z kolejnym krokiem: adapter podglądu i podstawowa
produkcja warstwowej paczki z UI, potem rzeczywista próba modeli oraz QA ruchu/zoomu.
